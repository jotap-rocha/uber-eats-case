## Context

Projeto: pipeline de dados Uber Eats (portfolio). Geração sintética via ShadowTraffic, container
`gen-unified` definido em `docker-compose.yml`, config em `shared/gen/unified/uber-eats.json.template`
(fonte versionada) → `shared/gen/unified/uber-eats.json` (gerado, git-ignored, nunca editado à mão).

**Por que o restart periódico é necessário:** quase todo generator do config tem um teto vitalício
por execução de processo — `localConfigs.maxEvents` (`restaurants`, `products`, `inventory`, `users`)
ou `fork.maxForks` combinado com `keepAlive: true` (`orders`, `payments`, `order_items`). Ao atingir
o teto, aquele generator para de emitir eventos **para sempre** dentro daquele processo Java; só um
restart do container libera nova cota. Restart "cru" (`docker-compose restart`/`stop`+`start`) é
proibido: colide PK porque `startingFrom` é um valor fixo no `uber-eats.json` gerado — ver
`.claude/kb/shadowtraffic/patterns/restart-seguro-startingFrom.md` (incidente real: 17 streams
travados, CPU 99%, zero linhas novas). O caminho seguro obrigatório é
`scripts/shadowtraffic/toggle-shadowtraffic.ps1` — a ação `on` roda `Sync-StartingPoints` (recalcula
`startingFrom` a partir de `MAX(id)` real via `shared/gen/setup-configs.ps1` + queries
Postgres/Oracle) **antes** de subir o container.

**Padrão de loop em background já existente** (a copiar, não reinventar):
`scripts/shadowtraffic/toggle-shadowtraffic.ps1` já implementa um loop de report horário via
`Test-ReportLoopRunning` / `Start-ReportLoop` / `Stop-ReportLoop`, disparando
`shadowtraffic-report-loop.ps1` como processo oculto (`Start-Process powershell -WindowStyle Hidden`),
com PID em `logs/report.pid` e log em `logs/shadowtraffic-report.log`. `shadowtraffic-report-loop.ps1`
se auto-encerra quando detecta `gen-unified` parado (checa `Test-ContainerRunning` antes de cada
ciclo). `on` chama `Start-ReportLoop`; `off` chama `Stop-ReportLoop`. `scripts/lib/shadowtraffic-common.ps1`
tem os helpers compartilhados (`Get-RepoRoot`, `Get-EnvVars`, `Test-ContainerRunning`,
`Wait-ContainerHealthy`, `Get-GeneratorSnapshot`).

**Decisão de arquitetura já tomada nesta sessão (registrar, não redescobrir) — como o loop de
restart sobrevive ao próprio ciclo sem duplicar instâncias:**

O loop de restart (`shadowtraffic-restart-loop.ps1`) chama `toggle-shadowtraffic.ps1` via operador de
chamada `&` (ex.: `& $togglePath -Action off`), **nunca via `Start-Process`** — em PowerShell, `&`
executa o script no **mesmo processo** (mesmo `$PID`) do script chamador; `Start-Process` criaria um
processo filho novo. Isso é o que torna a auto-preservação possível:

1. Quando o loop dispara um ciclo, ele mesmo (processo com PID `X`, já registrado em
   `logs/restart-loop.pid` por `Start-RestartLoop`) executa `& $togglePath -Action off` **dentro do
   seu próprio processo**. Dentro de `toggle-shadowtraffic.ps1 off`, `Stop-RestartLoop` lê
   `logs/restart-loop.pid` e encontra o PID `X` — que é o **próprio processo em execução**
   (`$PID -eq $X`, comparação disponível na função porque roda no mesmo processo).
2. `Stop-RestartLoop` deve reconhecer esse caso (`$procId -eq $PID`) e **não matar o processo**
   (pular `Stop-Process`), apenas registrar em log que o loop de restart vai sobreviver ao ciclo por
   ser o autor do próprio `off`. O arquivo `restart-loop.pid` permanece intacto.
3. Em seguida o mesmo processo executa `& $togglePath -Action on`. Dentro de `on`,
   `Start-RestartLoop` chama `Test-RestartLoopRunning` — o PID em `restart-loop.pid` (ainda o
   próprio `$PID X`) está vivo, então `Start-RestartLoop` **não** spawna um novo processo. Nenhuma
   duplicidade, nenhum órfão.
4. Se `off` for chamado por **outro caller** (usuário rodando `.\toggle-shadowtraffic.ps1 off`
   manualmente num terminal separado, processo diferente), `$procId` (do `restart-loop.pid`) será
   diferente do `$PID` desse terminal chamador — nesse caso `Stop-RestartLoop` mata o loop
   normalmente (comportamento correto: usuário pediu para desligar tudo).

Esta é a única forma correta de implementar o requisito — não implementar variantes com
`Start-Process -Wait` para os sub-chamados de `off`/`on` dentro do loop (isso criaria um processo
filho cujo PID nunca bate com o salvo em `restart-loop.pid`, e mataria o processo pai/loop no meio do
ciclo antes de ele conseguir chamar `on`, quebrando o encadeamento).

## Notes

- **Decisão de auto-preservação confirmada** por `@the-planner` (Iteration 1) — a arquitetura
  central proposta em **Context** (comparação `$PID -eq $procId` dentro do mesmo processo,
  invocação via `&` e nunca `Start-Process` para os sub-chamados de ciclo, `Stop-RestartLoop`
  pulando `Stop-Process` quando o `off` é autodisparado) está **correta e foi implementada como
  descrita**. O `&` executa o script-alvo no mesmo `$PID` do chamador (escopo de script filho —
  `param`/`ValidateSet`, dot-source de `shadowtraffic-common.ps1`, funções e
  `$ErrorActionPreference` ficam contidos nesse escopo e não vazam nem quebram a segunda chamada),
  o que valida a comparação de PID. Corridas com chamadas externas (`off` de outro terminal mata o
  loop corretamente; `on` externo entre o `off` e o `on` do próprio ciclo cai no ramo "já ativo" e
  não recalcula `startingFrom`, sem colisão de PK) são aceitáveis para o caso de uso real (processo
  único, execução local, usuário único) — não foi necessário lock distribuído nem
  `Start-Process -Wait`.

  A validação apontou **4 ajustes concretos**, incorporados na implementação (2 bloqueantes, 2
  recomendados):
  1. **(Bloqueante) Tratamento de `exit`/exceção por ciclo.** `toggle-shadowtraffic.ps1` usa
     `exit 1` em alguns caminhos de erro; chamado via `&`, isso não lança exceção nem mata o loop —
     só define `$LASTEXITCODE` e retorna silenciosamente. Implementado: `$LASTEXITCODE` zerado
     antes de cada `&`-call, cada chamada (`off` e `on`) dentro de seu próprio `try/catch`, checagem
     de `$LASTEXITCODE` depois, `on` sempre tentado mesmo se `off` falhar (é idempotente — cai no
     ramo "já ativo" se o container ainda estiver de pé), falha registrada no log e o `while`
     continua em vez de morrer. Crash duro do processo no meio do ciclo é aceito como fail-safe
     (container fica desligado, visível em `status`) — não fail-silent-infinito.
  2. **(Bloqueante) Loop de restart lançado com `pwsh`, não `powershell` 5.1.**
     `Sync-StartingPoints` usa `ConvertFrom-Json -Depth 100`, parâmetro que só existe a partir do
     PowerShell 6.2+; `-File` resolvido via `powershell` (5.1, mesmo padrão hoje usado por
     `Start-ReportLoop`) quebraria a primeira chamada de `on` dentro do ciclo. `Start-RestartLoop`
     usa `pwsh` explicitamente no `Start-Process`, diferente de `Start-ReportLoop` (que não chama o
     toggle, então não tem essa dependência).
  3. `Start-RestartLoop` chamado nos dois pontos onde `Start-ReportLoop` já é chamado hoje (ramo "já
     ativo" e ramo de subida normal) — já estava especificado na task CORE correspondente, apenas
     confirmado pela validação.
  4. **(Recomendado, custo baixo) Validação de identidade do PID.** Reaproveitamento de PID pelo
     Windows com um `restart-loop.pid` obsoleto causaria falso positivo em
     `Test-RestartLoopRunning`. Implementado apenas para o novo `Test-RestartLoopRunning`
     (`Get-CimInstance Win32_Process` conferindo que o `CommandLine` contém
     `shadowtraffic-restart-loop`) — não aplicado retroativamente ao `Test-ReportLoopRunning`
     existente, por estar fora do escopo deste PROMPT (gap pré-existente, não introduzido aqui).
  - Detalhes menores confirmados como já cobertos pelo desenho original: o loop dorme antes do
    primeiro ciclo (evita restart imediato ao subir) e o intervalo é efetivamente contado a partir
    do fim de cada ciclo (o `Start-Sleep` da próxima iteração começa logo após o ciclo anterior
    terminar). O `off` dentro do ciclo também reinicia o report loop com PID novo a cada 2h — já é
    o comportamento existente e é inofensivo.

- Usuário já aprovou execução direta sem revisão fase a fase — este PROMPT foi gerado sem pausar
  para perguntas, seguindo a especificação completa fornecida na conversa principal.
- Decisão de arquitetura chave (auto-preservação do loop de restart via invocação `&` no mesmo
  processo + comparação `$procId -eq $PID` dentro de `Stop-RestartLoop`) já está registrada em
  **Context** acima; a task 🔴 correspondente pede apenas validação/ajuste por `the-planner` antes de
  codificar, não redescoberta do zero.
- Regra inegociável (documentada em `restart-seguro-startingFrom.md` e reforçada aqui): nenhuma task
  deste PROMPT pode introduzir `docker-compose restart`/`stop`/`start gen-unified` direto — tudo
