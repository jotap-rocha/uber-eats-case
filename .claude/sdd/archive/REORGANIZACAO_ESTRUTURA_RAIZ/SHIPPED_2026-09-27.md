## Lessons Learned

### Process

- **Rodar `/intake` antes do `/design` para validar as Open Questions do DEFINE por inspeção real (em vez de assumir) encontrou 2 erros factuais no DEFINE v1.0** — o script "CDC configure" era SQL Server legado/órfão, não Postgres genérico comum às 3 nuvens (A-003), e a Constraint que mandava `sql/oracle/*.sh` para `scripts/` contradizia o fato de serem scripts de init de container executados em ordem junto com os `.sql`. Corrigir isso no DEFINE (v1.1) antes do `/design` evitou que a arquitetura fosse desenhada sobre uma premissa errada.
- **Delegar `/design` e `/build` a agentes em background (fork) manteve o "custo de contexto" baixo mesmo numa feature de blast radius grande** (~90 arquivos) — o `/build` sozinho consumiu ~545k tokens de subagente e 332 tool calls, volume que teria sido inviável manter na conversa principal.
- **Pedir confirmação explícita do usuário sobre o modo de execução do `/build`** (branch dedicada + commit por etapa, vs. sem commit automático, vs. etapa a etapa) antes de iniciar uma operação com blast radius de ~90 arquivos e múltiplos `git commit` foi o ponto certo para parar e perguntar — a regra "nunca commitar sem pedido explícito" não se resolve sozinha só porque o DEFINE já mandava usar branch dedicada.

### Technical

- **Mover pastas muda a profundidade de `$PSScriptRoot`/`Split-Path -Parent` em cascata** — 9 scripts PowerShell dependiam da profundidade antiga da árvore para calcular a raiz do repo; isso não estava no file manifest original do DESIGN (só apareceu executando os scripts após o move). O DESIGN previu um helper único de repo-root exatamente para este risco (R8 do `/intake`), mas a correção fina ainda exigiu tocar em cada script individualmente.
- **O mesmo problema de profundidade existe em Terraform** — 6 recursos usando `path.module` relativo quebraram com a nova profundidade de pastas; só apareceria num `terraform plan` real (CLI não disponível neste ambiente), então a correção foi por inspeção manual de cada `.tf`, não por validação automatizada.
- **`databricks.yml` não referenciava `pipeline/` de forma alguma** (sem bloco `resources:`/`include:`) — a suposição do DEFINE original de que "jobs/pipelines precisam ser atualizados" (AT-003) era desnecessariamente pessimista; a validação real (`databricks bundle validate`) falha só por falta de token/perfil local, não pelo reorg. Reescopar o teste evitou tratar uma limitação de ambiente pré-existente como um bloqueio da feature.
- **`git add` com pathspec amplo pode silenciosamente deixar arquivos fora do commit** — um commit da Etapa 2 perdeu 5 edições porque o pathspec usado não cobria todos os arquivos alterados; só foi percebido comparando o diff esperado (do DESIGN) com o que de fato foi commitado, reforçando a prática de conferir `git status`/`git diff --stat` após cada commit de etapa, não confiar no comando de `add` cego.

### Communication

- **O usuário pediu para "aplicar as correções ao define primeiro" antes de seguir para `/design`** — uma pausa deliberada de 1 turno entre "os agentes encontraram 2 erros no DEFINE" e "avançar para Design" que evitou carregar erros conhecidos para a fase seguinte só por inércia do fluxo `/intake → /design → /build`.
- **Perguntar o nível de autonomia de commit antes do `/build`** (em vez de assumir que "branch dedicada" já implicava autorização para commitar livremente) deixou explícito, por escolha do usuário, que o padrão seria commit por etapa — isso se mostrou o nível certo de granularidade para depois isolar e corrigir o bug do `git add` de pathspec sem perder trabalho de etapas anteriores.
