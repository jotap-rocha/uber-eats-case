## Lessons Learned

### Process

- **Perguntar "isso é código ou conceito?" antes de aceitar um princípio do roadmap como fechado evitou uma inconsistência silenciosa.** O `/define` descobriu que o brainstorm (seguindo a proposta literal do usuário) contradizia o princípio "Portabilidade de motor por camada" (v1.2), que prometia substituir Oracle/MinIO por serviços nativos AWS. Resolver isso explicitamente no `/define`, em vez de deixar passar, evitou que o `/design` fosse construído sobre uma premissa que o próprio roadmap já tinha descartado.
- **Sequenciar a implementação em etapas (Warehouse → Lakehouse → Kappa) por pedido explícito do usuário reduziu o raio de risco de concorrência de CDC** (2 tasks DMS lendo o mesmo replication slot/LogMiner) para uma única janela conhecida, em vez de um regime permanente — mesmo padrão de mitigação já usado nas Ondas 1-3, agora aplicado deliberadamente por pedido direto, não por repetição de convenção.

### Technical

- **DMS não é uma ferramenta de cópia de objetos.** A tentativa inicial de usar DMS para o MinIO (fonte object storage) foi corrigida a tempo — DMS só fala com motores de banco de dados; AWS DataSync (location "Self-managed object storage") é a ferramenta certa para esse caso, e isso só ficou claro perguntando diretamente "o DMS não consegue fazer isso?" em vez de assumir.
- **MinIO não assina requisições com SigV4** — a Function URL da Lambda ponte não podia usar `authorization_type = "AWS_IAM"` como o DESIGN sugeriu; a autenticação real precisa ser um token compartilhado validado dentro do handler. Esse erro só apareceu ao escrever o teste de rejeição de token inválido, não na revisão visual do código.
- **DataSync exige um agente de rede** (não documentado no DESIGN original) para acessar object storage self-hosted — adicionado no `/build`, com a ativação da chave marcada como passo manual (limitação real do serviço, não do design).

### Tools

- **`moto` permitiu testar as 2 Lambdas contra Kinesis/S3 mockados de verdade**, não só leitura visual do código — os 10 testes rodaram e passaram antes de qualquer deploy real existir, pegando o bug de autenticação da ponte antes que ele chegasse a produção.
- **`terraform validate` não pôde rodar neste ambiente sandboxado** (certificado TLS falha no handshake local entre o core do Terraform e o plugin do provider) — mitigado com revisão manual completa dos 12 arquivos `.tf`; fica registrado como limitação de ambiente a reproduzir/confirmar quando o usuário rodar isso no ambiente normal dele.

### Communication

- **O usuário decidiu explicitamente fazer o `/ship` mesmo sem validação contra AWS real**, quebrando conscientemente o padrão de rigor das Ondas 1-3 (que só arquivavam depois de validar contra infraestrutura rodando de verdade) — decisão registrada aqui para não ser lida como descuido em revisões futuras: é uma escolha deliberada, dado que a conta AWS só abre no início real da execução da Fase 2 (princípio já fixado no roadmap desde a v1.0).
